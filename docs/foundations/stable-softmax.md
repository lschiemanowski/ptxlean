# Stable softmax: the numerical foundation

Softmax turns scores into weights. For a nonempty row of real scores `x`, write

```text
m   = max_i x_i
z_i = x_i - m
e_i = exp(z_i)
Z   = sum_i e_i
p_i = e_i / Z
```

Subtracting the same maximum from all scores leaves the exact softmax unchanged.
Every `z_i` is nonpositive, and at least one is zero. Consequently every `e_i`
is positive and at most one, at least one is one, and `1 ≤ Z ≤ row length`.
This is a fact about real arithmetic. Subtracting two finite machine numbers can
still overflow, so a future kernel must prove a range bound for its subtraction.

The reference is the actual stable softmax in the pinned TorchLean dependency,
not a second definition of the intended network. The bridge in
[`PtxSoftmaxAccuracy.lean`](../../integration/torchlean/PtxSoftmaxAccuracy.lean)
exposes that specification's coordinates and reuses its checked analysis.

## Following the error through the forward computation

A machine implementation computes approximations at each stage. We give each
stage a separate absolute-error obligation:

| Stage | Actual value | Local obligation |
|---|---|---|
| Shifted exponential | `u_i` | `abs(u_i - e_i) ≤ delta_i` |
| Sum of computed exponentials | `S` | `abs(S - sum_i u_i) ≤ sigma` |
| Reciprocal of the computed sum | `r` | `abs(r - 1/S) ≤ rho` |
| Final multiplication | `pHat_i` | `abs(pHat_i - u_i*r) ≤ tau_i` |

The summation error refers to the **computed** exponentials, and the reciprocal
error refers to the **computed** sum. Neither can substitute ideal operands.
`delta_i` must eventually include input representation, subtraction, conversion
of an exponential's base, and the exponential instruction's own error.
These contributions have not yet been discharged by an instruction proof.

Set `D = sigma + sum_i delta_i`. The triangle inequality gives
`abs(S-Z) ≤ D`. Thus `S ≥ 1-D`. When `D < 1`, the computed sum is strictly
positive and the proof can bound division by it. The checked coordinate bound is

```text
abs(pHat_i - p_i) ≤ tau_i + (1 + delta_i)*rho + (delta_i + D)/(1-D).
```

The three terms account for final multiplication, reciprocal error, and the
perturbed numerator/denominator. The sum of these coordinate bounds controls
`abs(sum_i pHat_i - 1)`. The computed weights need not sum to exactly one, and a
small exact exponential may become zero. Both possibilities have checked
regression examples. The row length matters because `D` accumulates all the
exponential errors and the sum's rounding error. `D < 1` is a sufficient guard
for this estimate; failing it does not establish that a particular computation
is incorrect. No practical tightness claim has yet been made for a PTX kernel.

[`SoftmaxError.lean`](../../integration/torchlean/PtxBinary32/SoftmaxError.lean)
proves these implications for every set of stage values satisfying the local
contracts. `exact_stages` supplies a real-arithmetic witness with zero errors.
It is deliberately **not** a binary32 representability or kernel-execution
witness. Lean's real division is defined even at zero; the positivity theorem
and a counterexample with `D=1, S=0` ensure this total mathematical operation
cannot silently justify a machine reciprocal.

## Following the error through backward

An incoming sensitivity `d_i` describes how strongly output `i` contributes to
the surrounding computation. The real input sensitivity is

```text
q   = sum_j p_j*d_j
g_i = p_i*(d_i-q).
```

TorchLean proves this is the vector–Jacobian product of the true derivative of
its forward function. This is not a derivative of rounding. Unlike ReLU, this
smooth reference does not require an assumption excluding a corner point.
The bridge's `backward_is_vjp` exposes that exact dependency.

Let the computed forward weights be `pHat`, the represented incoming
sensitivities be `dHat`, and their respective errors be `epsilon` and `eta`.
A supplied backward computation first forms a dot product, then a subtraction,
then a multiplication. If its dot-product error relative to its actual operands
is `sigmaDot`, define

```text
Q = sigmaDot + sum_j (abs(d_j)*epsilon_j + abs(pHat_j)*eta_j).
```

This bounds the computed dot product's error against `q`. If the subtraction
and final multiplication have local errors `subError_i` and `mulError_i`, then

```text
abs(gHat_i - g_i) ≤ mulError_i + abs(d_i-q)*epsilon_i
                   + abs(pHat_i)*(subError_i + eta_i + Q).
```

`backward_error_of_forward` substitutes the proved forward error for `epsilon`;
it does not require the caller to assume that forward result again. Incoming
sensitivity error remains separate. No PTX backward program is generated by
this theorem. The backward kernel and its implementation proof remain separate
work from TorchLean's reverse computation.

## What the PTX 9.4 source says, and what remains interpretation

The pinned source is recorded by
[`manifest.json`](../../references/nvidia/ptx-isa-9.4/manifest.json), SHA-256
`0aa31c15735a30b5d7c0fa1fe02570dcd37fe80800afca74bcc96c9132b81fed`.
The following is our paraphrase of the relevant contracts; the NVIDIA document
is fetched locally and is not redistributed.

- [`ex2.approx.f32`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#floating-point-instructions-ex2)
  computes a base-two exponential. Its stated allowance is two units in the last
  place from the correctly rounded result. Zero maps to one; negative infinity
  maps to positive zero; positive infinity stays positive infinity; NaN remains
  NaN. The optional `.ftz` form flushes subnormal inputs/results to signed zero.
  For `sm_20` and later, the form without `.ftz` retains subnormal handling.
  The explicit approximation modifier is required starting with PTX 1.4.
- [`rcp.approx.f32`](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#floating-point-instructions-rcp)
  has a stated one-ULP allowance. Its accuracy wording does not explicitly use
  the same correctly-rounded reference phrase as `ex2`; we have not silently
  assigned it that interpretation. Signed zeros and infinities exchange roles
  under reciprocal, preserving sign, and NaN stays NaN. The source also provides
  explicit rounding forms; explicit-rounding `f32` reciprocal requires `sm_20`.

A unit in the last place (ULP) is a spacing on the floating-point grid. At a
power of two, the spacing differs on the two sides. Our reusable
[`Approximate.lean`](../../integration/torchlean/PtxBinary32/Approximate.lean)
uses the pinned FloatLib/TorchLean ULP evaluated at the center. This convention
is explicit, but is not yet a proved interpretation of NVIDIA's wording.
Its finite error neighborhood contains all encoded finite values at most the
chosen distance from a supplied finite center word. It includes its center
and preserves alternative results. Infinity and NaN are excluded; their
instruction cases require separate rules. Even radius zero does not identify
bits: positive and negative zero have the same real value.

If a center is itself within error `E` of the ideal value, every neighborhood
member is within `radius + E`. In particular, an approximation allowance around
a correctly rounded result must include the center's rounding error when
comparing with the ideal exponential. The bridge in
[`RoundedReal.lean`](../../integration/torchlean/PtxBinary32/RoundedReal.lean)
now constructs that encoded center whenever the ideal value's absolute value is
at most binary32's maximum finite value. It rounds to an integer times a power
of two, proves the rounded value stays in range by monotonicity, and packs it
using FloatLib's checked dyadic rounding. Packing is exact because the value is
already on the binary32 grid. Neither an output word nor its finiteness is a
premise. This is a non-executable mathematical witness, suitable for relational
semantics; it is not an executable exponential implementation.

In particular, every nonpositive real base-two exponent has an encoded center
and a nonempty approximate-result neighborhood. The bound is uniform over all
admitted results: for an ideal value in `[0,1]`, a count-k neighborhood has
absolute error at most `(k+1/2)*2^-23`. Thus the two-ULP convention gives
`5*2^-24`, including the center's rounding error. This does not include argument
preparation errors yet. The proofs include zero and gradual underflow.

The ULP choice remains explicit. A checked boundary example shows that two
center ULPs below the value one span four steps in the positive encoding order.
Replacing the distance predicate by a difference between encoding integers
would therefore change the contract. The pinned manual does not define these
boundary conventions in the reviewed passages. We use center spacing for the
numerical foundation, but do not mark a PTX instruction covered on that basis.
An instruction review must justify the interpretation or a conservative envelope
covering the intended source meanings.

A future `ex2` path must also account for `exp(z) = 2^(z*log2(e))`: representing
the conversion constant, multiplying by it, and perturbing the input all
contribute error. Simply attaching a two-ULP allowance to `exp(z)` would omit
those operations. Maximum selection, shifts, summation order, reciprocal and
multiplication must eventually come from the fetched kernel and its actual
instruction operands.

## Checking and the next acceptance boundary

From the repository root, with the documented pinned Lean setup installed:

```sh
./scripts/check.sh
(cd integration/torchlean && ./check.sh)
```

The integration build includes the new numerical modules, TorchLean bridge and
[`SoftmaxChecks.lean`](../../integration/torchlean/PtxBinary32/SoftmaxChecks.lean).
The dependency audit checks every new public definition and theorem, including
structure contracts and fields. It rejects incomplete proofs and nonstandard
axioms. These checks establish the stated Lean propositions, not fidelity to
NVIDIA hardware or a performance result.

The initial reciprocal path selects `rcp.rn.f32`, which has an explicit
nearest-even rounding rule, rather than interpreting the approximate reciprocal's
unspecified error reference. [`Reciprocal.lean`](../../integration/torchlean/PtxBinary32/Reciprocal.lean)
supplies checked, executable encoded division of one by the actual input word,
with the existing conservative NaN envelope. From a finite nonzero operand and
an exact-quotient range bound it derives finite output, rounded-real equality
and a half-ULP error bound. Its encoded checks include signed zeros, infinities,
a rounded third, a subnormal result, overflow and alternative NaN payloads.
The accepted unary leaf in `PtxBinary32/ReciprocalInstruction.lean` now connects
actual fetch, target checks, both predicate polarities and unrestricted aliases to
this numerical relation. It preserves every admitted output. Its typed decoder
accepts exactly `rcp.rn.f32`; raw PTX parsing remains outside this interface.

The positive-denominator proof alone is insufficient to rule out reciprocal
overflow. A useful stronger guard is `D ≤ 1/2`: then the computed sum is at
least `1/2`, its reciprocal is at most two, and the provider derives an actual
finite result from these input conditions. Its `result_exists_of_sum_error`
theorem makes this handoff explicit without an assumed successful reciprocal.

The [unary-instruction preflight](../formalization/unary-floating-preflight.md)
records the remaining exponential acceptance obligation. The reciprocal leaf
was authored by Luna and accepted after fresh independent checks and separate
source/proof reviews. Only `rcp.rn.f32` is covered; no `ex2` coverage is claimed.
The checked `ApproximatePolicyChecks` example also shows that output-spacing
ULPs can admit a pair excluded by center-spacing ULPs. Adopting the existing
center relation as PTX would therefore require a source justification, not just
a Lean proof. Remaining kernel work includes
parallel maximum and sum programs, forward and separately supplied backward
programs, memory safety, admitted execution witnesses, and universal stored
output bounds. The first row is nonempty and unmasked. Empty/all-masked rows,
attention, GPU runs and benchmarking are outside this slice.
