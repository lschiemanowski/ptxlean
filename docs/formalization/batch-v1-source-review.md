# Source and proof review of three pure families

The coordinator compared each candidate with the locally acquired, hash-pinned
PTX ISA 9.4 manual identified by
[the source manifest](../../references/nvidia/ptx-isa-9.4/manifest.json).
The leaf definitions were generated by Luna from coordinator-written contracts.
Source interpretation, Lean proof checking and GLM's advisory opinion are
separate evidence. This review covers five selected forms, not whole instruction
sections or hardware behavior.

| Family | Selected forms | Instruction section | Version and numeric feature floor |
| --- | --- | --- | --- |
| Bit reversal | `brev.b32` | `integer-arithmetic-instructions-brev` | PTX 2.0, SM at least 20 |
| High-half multiplication | `mul.hi.u32`, `mul.hi.s32` | `integer-arithmetic-instructions-mul` | PTX 1.0, SM at least 10 |
| Field extraction | `bfe.u32`, `bfe.s32` | `integer-arithmetic-instructions-bfe` | PTX 2.0, SM at least 20 |

The implemented version slice is exactly ISA 94. The numeric SM floor records a
feature requirement; it does not validate actual architecture names or suffixes.
Both positive and negative guards use the existing shared execution rule. A
fetched instruction still checks its target condition when its guard is false.

## Relating definitions to the manual

Bit reversal maps output position i to input position 31-i. The pinned Lean
`BitVec.reverse` recursively reverses the lower bits and appends the original
high bit. It reverses bits, rather than just the four bytes. Checked examples
include one, zero, all ones and an asymmetric pattern whose reversal is distinct
from byte reversal.

High-half multiplication first interprets both inputs with the selected signedness.
The unsigned definition divides the exact natural-number product by 2^32. The
signed definition uses exact integer multiplication followed by division by the
positive integer 2^32, which in Lean rounds downward. Re-encoding the quotient as
32 bits produces the high half of the full product, including negative products.
No intermediate 32-bit multiplication loses the high half. In particular, signed
minus one times one has high half all ones; signed minus one times minus one has
high half zero. These distinguish signed interpretation and downward rounding
from unsigned multiplication and truncation toward zero. Minimum signed inputs
and unsigned carry into the high half are also checked.

Field extraction reduces the position and length modulo 256, matching the
manual's use of their low eight bits. The fold visits result bit positions zero
through 31 exactly once. A copied input bit contributes 2^i to the result; each
other position receives the specified fill bit. For signed extraction with a
nonzero length, that fill bit is input bit min(position+length-1,31). Zero length
forces zero fill and copies nothing. Thus a field beyond the input can produce
all ones for a negative input. Natural-number subtraction is used only where
zero length has already disabled the sign bit. Positions and lengths above 255
are admitted, not excluded by a hypothesis.

The field-extraction section's example uses `bfe.b32`, although its syntax lists
signed and unsigned forms. This slice follows the syntax and rejects that example
spelling. It does not silently extend the decoder or claim the documentation
inconsistency has been resolved. All other widths and options remain excluded.

The common operand and guard sections were also checked. Destination and source
registers must have compatible declarations; input immediates are supplied as
already converted words. A typed token interface is not a complete PTX parser,
register type checker or launch interface. These obligations are stated rather
than hidden in a proof of runtime correspondence.

## Proof review

The coordinator inspected each full candidate: computation, family construction,
lowering, guarded transitions, event fields, target conditions, decoder and every
required theorem statement. The frozen driver assigns all eighteen universal
statements at their required types, without additional premises. They quantify
over arbitrary input words and registers; aliases and repeated operands remain
possible. Boundary examples check concrete values, target floors, both guard
polarities, repeated reads, exact spelling and malformed/unsupported distinctions.

Each family uses the original `Pure32.Eval` and `Pure32.Step`, not a local
replacement. Source operands are evaluated in the incoming state; only the word
destination and next instruction position change. Disabled instructions record
only guard reads. Existence is one-step existence under target/fetch conditions,
not whole-kernel termination. Determinism is a proved property of these selected
functions, not a new premise imposed on all families.

Fresh replay builds the pinned base independently, applies the exact recorded
patch, runs the unchanged driver, and audits every public definition and theorem.
Only standard Lean logical axioms are permitted. The coordinator reference
fixtures used to test the drivers were withheld from worker checkouts. They were
created by adapting existing proof templates; they are neither model output nor
independent evidence that the source interpretation is right.

See [the batch report](../../formalization/results/batch-v1/README.md) for invocation
outcomes, preflight work, blinded review, costs and reproducibility commands.

## Adjudicating the later model findings

The checked [adjudication examples](../../formalization/review/batch-v1/adjudication.lean)
refute GLM's claim about truncated integer division and compute its proposed
extraction inputs under both signednesses. Packet inspection confirms the
extraction definition and both reductions modulo 256 were supplied in full.
Positions and lengths are natural numbers after word decoding, so their additions
are not silently performed in a 32-bit word.

For constants, the source-operands section describes the register state space
for ALU operands, while the instruction-statements section explicitly admits
constant expressions and the integer-constants section describes their conversion
at instruction use. The project reads these together: register variables must
reside in registers, and already converted constants are also accepted by these
typed interfaces. The chosen interpretation is explicit; this review does not
establish raw assembler acceptance. Rejecting every immediate would contradict
the supplied contract and the general constant-operand provisions. No claimed
model counterexample demonstrated a defect in the accepted leaves.
